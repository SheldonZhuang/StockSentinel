# Lessons（用户更正后沉淀的规则）

## 2026-09-17 · 用户给的通用原则，落地时先做"是否普适"的判定，再动手（128号）
**场景**：用户要求"参考指标里的所有参数，一经公布就在网页上立即更新"。照字面全改会**破坏系统**：
WTI油价/信用利差/收益率曲线/EPU日频这几个是**连续行情型**，而系统按"每日21:00采样点"记 track record
——盘中实时化会让采样点从"固定时点"漂移成"最后一次访问的时刻"，历史序列失去可比性，回测（锚定收盘口径）
也随之失效。真正该实时化的是**离散事件型**（FOMC决议、08:30的BLS/BEA月度发布）：公布时刻固定、结果一经
公布即永久确定，等21:00纯属无谓滞后。
**规则**：用户提出"所有X都要Y"式的通用原则时，先按**数据发布节奏**给 X 分类，找出"做了会坏"的那一类，
把边界**明说给用户**（含代价），再对安全的那一类动手。不要两种错误：①照字面全改造成静默破坏；
②因为存在边界就整体不动。本轮的做法是：抽取通用引擎只覆盖 A 类，B 类在文档/代码注释里写明"有意为之"，
并在todo里留一条待用户拍板的口子。

## 2026-09-17 · 判定链的"预期值"必须来自读代码，不能凭直觉写测试（127号/128号连踩两次）
**事故**：给事件刷新引擎写测试时，我按直觉预期"财政转tight + 货币tight → 双维共振 → defense"，
实际两次都得到 reduce：第一次是 X3 规则（纯货币+财政共振降为 reduce），第二次是趋势再入场
（上升趋势中树驱动的 defense 降为 reduce）。**两次都是我的测试预期错，引擎是对的**。
**规则**：写判定链测试前，先 grep 出该档位路径上的**全部**后置变换（否决器/趋势再入场/趋势地板/迟滞/X3），
确认每一步的输入输出。测试失败时第一反应是"读实现"，而不是改实现去迎合预期——本轮若图省事放宽引擎，
就会在生产里制造一个比判定树更松的旁路。**判定链的测试预期来自代码，不来自推理。**

## 2026-09-17 · "外部数据的官方发布源"必须与"我们订阅的取数序列"分开评估（127号）
**事故**：FOMC 9/16 加息 25bp，系统当晚写出的快照把方向判成"暂停→宽松"（货币维 loose，方向反了），
网页显示"0.00%（持平）"。根因不是代码 bug，是**把日更序列当成了决议结果的实时源**：FRED DFEDTARU
要到次一工作日才有新台阶，而决议本身美东 14:00 就已由 Fed 官网公布。既有护栏 decisionDataPending
只做到"沿用上一快照基线"——它防住了"误报宽松"，却把结果锁在"持平"上，方向仍是错的。
**规则**：凡"事件驱动"的宏观数据（FOMC 决议、财报、指引），都要问一句"**事件本身在哪一刻可被观测**"，
再决定取数源；序列型数据源（FRED）只适合做历史基线，不适合做事件当天的方向判定。判定链的取数源
一旦换，`prevRate/stepBp/currentRate` 三者必须**同源推导**（本轮踩到：prevRate 取区间下界而幅度按旧上限算，
50bp 场景会自相矛盾）。
**护栏的边界也是教训**：一个"防某个错误方向"的护栏，如果不能让状态变正确，就只是让错误更隐蔽
（"持平"看起来比"宽松"无害，但决策含义同样是错的）。修复这类问题时，要给护栏加**退出条件**
（本轮：`rateSource === 'fed_statement'` 时旧护栏必须让位），否则它会覆盖正确的数据。

## 2026-09-17 · 改 INSERT 的列清单时，必须数占位符（127号线上真实 bug）
**事故**：给 saveSignalSnapshot 加一列 `rate_source` 时列清单加到了 95 列，VALUES 占位符却成了 96 个，
线上表现为 `[cron] Signal updated` 之后紧跟 `Error: 96 values for 95 columns` ——**决议后的第一次完整
落库直接失败**，且失败发生在 saveSignalSnapshot（写入链第一环），后续告警/S5 邮件全部不执行。
**规则**：动 `INSERT INTO ... (cols) VALUES (?,...)` 之后立刻跑一次**真实写入**验证（临时 DB_PATH
指向副本库，调一次 saveSignalSnapshot 再读回），不能只看单测——单测全绿是因为没有一条用例覆盖
saveSignalSnapshot 本身（34 个测试文件里 0 个引用它）。这是"缺测=缺证据"的典型。
**顺带**：这类错误在日志里长得像普通运行时异常，容易与业务错误混淆；判据是看**列数**而不是看堆栈。

## 2026-07-18 · 重大新判定输入不能只靠"一并执行"式的批量授权（用户88号质疑）
**规则**：凡是**新增参与判定的输入**（哪怕只是否决器，如收益率曲线倒挂否决进攻档），上线前要在

## 2026-07-30 · 财报刚结束数小时内的 web 检索会命中赛前预览稿（用户112号送核发现）
**规则**：凡是"检索外部信息回填某事件的结果"类自动化（capex 指引、财报快报及未来同类），
必须带**时间维度的来源核验**：只采信事件发生时刻之后发布的报道；预览(preview)稿、
分析师预期不是当事人表述。落档前核对来源 URL 的发布日期与事件时刻的先后关系。
**历史教训**：MSFT FY26Q4 电话会结束数小时后系统即检索，5 条来源全是财报前预览稿，
指引记成旧计划 $190B+分析师推测 $220B，方向误判 raise；真实情况是会计变更重述 ~$175B、
实际计划维持（应判 maintain）。且本机与云端两个实例**各自独立污染**——数据修正必须
考虑多实例收敛（本次用启动自愈补丁模式，部署即收敛，勿只修本机）。

## 2026-07-30 · Windows 计划任务默认 72 小时执行上限会静默杀死长驻服务
**规则**：用计划任务承载**长驻进程**（非跑完即退的脚本）时，建任务当场必须显式设置：
ExecutionTimeLimit=0（不限时）+ RestartCount/RestartInterval（崩溃自拉起）+ 解除电池限制。
默认配置（72h 上限+不重启）等于给服务装了三天定时炸弹，且死后无人拉起。
**历史教训**：StockSentinel-Backend 7/25 启动的实例 7/27 日更中途被杀，7/27-29 三天
快照断档（track record 永久缺口，无法诚实回补）。此前 7/20 建任务时只解决了"开机自启"，
没审视"活得久"——运维配置要按"这个进程要活多久"倒推，不是能启动就算完。


## 2026-07-30（116号系统性审查）

- **外部 SDK 的错误语义必须实测**：Resend `emails.send` 对一切失败都 resolve `{data,error}`、
  从不 reject——按"失败会 throw"假设写的重试/告警全是死代码，且 mock 按同样假设写导致单测全绿。
  规则：写任何外部 SDK 的错误处理前，先读它的 dist 源码确认 reject/resolve 语义；mock 对齐真实语义。
- **防护机制两两组合的边界要专项审**：stale-keep×N3、override×锁龄、迟滞×快照断档、
  佐证门槛×LLM 自证——单个机制都对，组合时互相反噬。新增机制时逐一过一遍"与现有每个机制
  在故障日叠加谁优先"。
- **对外引用的数字要么单一来源要么标注快照日期**：SKILL 里的回测数字在 O1 采纳后过期 11 天
  无人发现（11.3% vs 引擎 12.1%）。规则：文档写"约X%（YYYY-MM-DD 快照，以实时接口为准）"，
  重跑回测的 checklist 里加"同步 SKILL/README 数字"。
- **双实例部署的每个"全局副作用"都要问归属**：邮件群发、备份上传、事件录入——两实例都跑就是
  双发/互踩。INSTANCE_ROLE 已建立；今后新增任何外发动作，先问"replica 该不该做"。

## 2026-08-15 · 报告"机密已暴露"前必须先 git grep 核实（121号收尾误报）
**事故**：向用户提醒"WebSocket 密钥明文已随 docs 推到 GitHub"，用户据此要求改占位符重推；
实际核查（git grep + git log -S 全历史 + 全盘 grep）发现密钥**从未入库**——文档里写的一直是
`MOOMOO_WS_KEY 的值`这种指代，明文只存在于 .env 与 .claude/settings.local.json（均被 ignore）。
误报源头：凭"我在排障文档里写过修复步骤"的印象推断"步骤里含明文"，没有回读自己写的文件。
**规则**：任何"泄露/暴露"类安全警告在说出口前，必须完成三查——①`git grep <secret>`（当前
已跟踪文件）②`git log -S <secret> --all`（全历史）③确认命中文件的 ignore 状态。安全误报
不是"宁可信其有"的免费保险：它消耗用户信任，还会触发无谓的改历史/换钥操作。
