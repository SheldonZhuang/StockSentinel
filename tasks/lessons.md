# Lessons（用户更正后沉淀的规则）

## 2026-07-18 · 悬停提示与判定规则必须同一提交内同步（用户87号更正）
**规则**：任何改动判定逻辑/阈值的提交（signal.config.js、signal.js、server 判定链），必须在**同一个提交**里同步：
1. frontend/src/i18n 七语言的 hints.* / hintGlobal / interpret.* / 档位描述；
2. skills/stock-sentinel/SKILL.md；
3. backend/api/mcp.js 与 mcp/index.js 的工具描述。
**自查方法**：改完规则后 grep 前端 locales 里涉及该维度的所有键逐条比对。历史教训：v2 判定上线后
七语言文案滞后了一天才被一致性审查发现（渐进加息旧文案），W5 上线时 defense 描述又漏了趋势例外。

**2026-07-20 扩展（103号审查教训）**：同步范围补两处更隐蔽的：
4. README.md 的信号计算表与全局叠加段——README 停在 MVP 三档/SMH-SPY 时代历经六轮判定迭代
   无人发现，外部访客看到的第一页与系统实际行为差了一代；
5. backend/api/daily-report.js 的 buildFacts 判定规则行——这是每天喂给 LLM 的解读依据，
   旧规则"进攻=四维全宽松"导致日报"距进攻还差什么"的解读一直基于错误规则。
**为什么隐蔽**：界面文案有用户天天看着，README/日报规则行没有日常曝光路径，只能靠提交纪律。

## 2026-07-18 · 重大新判定输入不能只靠"一并执行"式的批量授权（用户88号质疑）
**规则**：凡是**新增参与判定的输入**（哪怕只是否决器，如收益率曲线倒挂否决进攻档），上线前要在
回复里单独一段醒目说明"新增了什么判定角色、为什么、如何撤销"，并等用户看到；批量授权
（"其他的也一并执行"）只适用于修 bug、文案、口径对齐类，不适用于引入新判定维度。
历史教训：收益率曲线否决器随"一并执行"上线，用户事后表示"没有印象"。

## 2026-07-18 · 用户目标显著超出数学可行域时，先算天花板再讨论方案（用户89号）
**规则**：遇到"年化100%"类目标，不直接说不可能也不假装可行——先用回测数据算出该框架的
理论上限（如完美预知择时的年化），把目标、现状、天花板放在同一张表里给用户看，再给出
逼近天花板的现实路径（换标的/杠杆/集中度）及其代价。用户自己的 CLAUDE.md 要求"太离谱要指出来"。

## 2026-07-30 · 财报刚结束数小时内的 web 检索会命中赛前预览稿（用户112号送核发现）
**规则**：凡是"检索外部信息回填某事件的结果"类自动化（capex 指引、财报快报及未来同类），
必须带**时间维度的来源核验**：只采信事件发生时刻之后发布的报道；预览(preview)稿、
分析师预期不是当事人表述。落档前核对来源 URL 的发布日期与事件时刻的先后关系。
**历史教训**：MSFT FY26Q4 电话会结束数小时后系统即检索，5 条来源全是财报前预览稿，
指引记成旧计划 $190B+分析师推测 $220B，方向误判 raise；真实情况是会计变更重述 ~$175B、
实际计划维持（应判 maintain）。且本机与云端两个实例**各自独立污染**——数据修正必须
考虑多实例收敛（本次用启动自愈补丁模式，部署即收敛，勿只修本机）。

## 2026-07-30 · Windows 计划任务默认 72 小时执行上限会静默杀死长驻服务
**规则**：用计划任务承载**长驻进程**（非跑完即退的脚本）时，建任务当场必须显式设置：
ExecutionTimeLimit=0（不限时）+ RestartCount/RestartInterval（崩溃自拉起）+ 解除电池限制。
默认配置（72h 上限+不重启）等于给服务装了三天定时炸弹，且死后无人拉起。
**历史教训**：StockSentinel-Backend 7/25 启动的实例 7/27 日更中途被杀，7/27-29 三天
快照断档（track record 永久缺口，无法诚实回补）。此前 7/20 建任务时只解决了"开机自启"，
没审视"活得久"——运维配置要按"这个进程要活多久"倒推，不是能启动就算完。


## 2026-07-30（116号系统性审查）

- **外部 SDK 的错误语义必须实测**：Resend `emails.send` 对一切失败都 resolve `{data,error}`、
  从不 reject——按"失败会 throw"假设写的重试/告警全是死代码，且 mock 按同样假设写导致单测全绿。
  规则：写任何外部 SDK 的错误处理前，先读它的 dist 源码确认 reject/resolve 语义；mock 对齐真实语义。
- **防护机制两两组合的边界要专项审**：stale-keep×N3、override×锁龄、迟滞×快照断档、
  佐证门槛×LLM 自证——单个机制都对，组合时互相反噬。新增机制时逐一过一遍"与现有每个机制
  在故障日叠加谁优先"。
- **对外引用的数字要么单一来源要么标注快照日期**：SKILL 里的回测数字在 O1 采纳后过期 11 天
  无人发现（11.3% vs 引擎 12.1%）。规则：文档写"约X%（YYYY-MM-DD 快照，以实时接口为准）"，
  重跑回测的 checklist 里加"同步 SKILL/README 数字"。
- **双实例部署的每个"全局副作用"都要问归属**：邮件群发、备份上传、事件录入——两实例都跑就是
  双发/互踩。INSTANCE_ROLE 已建立；今后新增任何外发动作，先问"replica 该不该做"。


## 2026-07-31（117号 AMZN 旧指引回声）

- **"时间护栏"拦不住"内容回声"**：只过滤财报前发布的文章，拦不住 LLM 把财报前已知的旧指引
  金额当作本次 maintain 输出（财报当晚媒体覆盖不足时必然发生——已连续两季财报夜出现同族污染）。
  修法从"过滤输入"升级为"结构性自愈"：财报当晚的 web 档一律视为暂定、次日媒体覆盖到位后自动
  重检刷新。规则：对时效敏感的 LLM 采集任务，首次结果默认暂定+定时复核，而非一次定档。
- **同一事故的两实例镜像再次不同**（本机 consensus 推算 vs 云端旧计划 maintained）：LLM 输出
  的非确定性让"多实例同代码"不等于"多实例同数据"——数据修正必须走启动自愈补丁（已是第三次
  验证该模式），且补丁要配 manual_verified 类标记防被后续自动流程覆盖。

## 2026-08-04 · 陈述用户仓位/执行层状态前必须查实时状态（用户121号纠错）
**规则**：凡是回答"您现在该持有多少/系统让您持有多少"，必须先查 getCapeState() 与 S5 实时
目标仓位再落笔——CAPE估值层（>90分位→55%）是**独立于宏观档位**的仓位开关，凭"reduce期
持有不动"推断"目标100%"漏掉了估值层。历史教训：CAPE 41.51/P95.6 激活中，系统目标55%、
用户实盘50%，我却断言"存量满仓100%吃到反弹"——方向性结论(没踏空)侥幸成立，数字错了。
**引申**：向用户解释"为什么没有进攻信号"时，要先想清楚"就算有进攻信号，他的仓位会变吗"
——当前答案是不会(估值层封顶55%)，这才是对"我要更灵敏信号"最重要的回应。

## 2026-08-15 · 报告"机密已暴露"前必须先 git grep 核实（121号收尾误报）
**事故**：向用户提醒"WebSocket 密钥明文已随 docs 推到 GitHub"，用户据此要求改占位符重推；
实际核查（git grep + git log -S 全历史 + 全盘 grep）发现密钥**从未入库**——文档里写的一直是
`MOOMOO_WS_KEY 的值`这种指代，明文只存在于 .env 与 .claude/settings.local.json（均被 ignore）。
误报源头：凭"我在排障文档里写过修复步骤"的印象推断"步骤里含明文"，没有回读自己写的文件。
**规则**：任何"泄露/暴露"类安全警告在说出口前，必须完成三查——①`git grep <secret>`（当前
已跟踪文件）②`git log -S <secret> --all`（全历史）③确认命中文件的 ignore 状态。安全误报
不是"宁可信其有"的免费保险：它消耗用户信任，还会触发无谓的改历史/换钥操作。
