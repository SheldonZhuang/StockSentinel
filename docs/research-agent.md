# 公司研究 Agent

输入 SEC 申报（10-Q / 10-K / 8-K EX-99.1；TSM 为 20-F / 6-K），输出每家公司每季一份带出处的结构化研究笔记。只做研究参考，不给买卖建议，不做股价预测，**不参与股哨兵信号判定**。

覆盖：MSFT、GOOGL、AMZN、META、NVDA、AMD、AVGO、TSM（`backend/config/research.config.js`，加一行即可扩展）。

## 阶段 1：文档层

### 数据流

```
EDGAR submissions ──分类/财季归属──▶ 申报清单 ──下载(有缓存则跳过)──▶ HTML 原件(.gz)
   ──htmlToText──▶ 纯文本(.txt，出处基准) ──按 Item 标题切章节──▶ 章节 ──按段落切块──▶ chunks(research.db)
                                                                     └─▶ 数据质量检查 ──▶ dq_issues ──▶ 管理后台
```

- 存储：独立 `research.db`（不进主库，主库每次写入都全量导出）+ `data/filings/<accession>/` 原文缓存。都不进 GitHub 备份，可从 EDGAR 重建。
- EDGAR 访问统一走 `utils/edgar-client.js`：裸 UA、进程内全局串行限速（≥120ms 间隔）、429/5xx/超时退避重试，404/403 立即失败。股哨兵原有三处 EDGAR 调用已迁移过来。
- 出处字段：公司、表格类型、提交日期、accession、章节、Item、字符区间 `[char_start, char_end)`、原文链接。字符区间指向缓存的 `.txt`，`text.slice(start, end)` 与块正文逐字相同。
- 财季标识统一为"财年 + 财季 + 报告期末"（如 MSFT FY2026Q4 = 2026-06-30），52/53 周财年按容差归属。8-K 新闻稿归属到申报日前最近一个已结束的季度。
- TSM：XBRL 只有 20-F 年度数据。季度材料取两类 6-K，按主文档名识别：财报新闻稿 `tsm-YYYYMMDDx6k.htm` 和季度合并财报 `tsm-fsxYYYYMMDDx6k.htm`。月营收、董事会决议等 6-K 不收。
- 章节：MD&A、风险因素、财务报表、业务、市场风险、法律诉讼等按 Item 标题切分。分部收入、资本开支、指引是跨章节的话题，在块级打 `topics` 标签。
- 增量：已解析的 accession 不再下载；失败的最多重试 3 次，原因写进 `filings.error` 和数据质量清单。
- 数据质量：缺季（过了法定期限还没有文件；没过期限的记 pending，不算缺失）、同一季重复、解析失败、必需章节缺失或过短。最近一次运行的结果在管理后台「研究文档采集」面板可见，也可以在那里手动触发增量采集。

运行：`cd backend && node scripts/research-ingest.mjs [TICKER ...] [--as-of=YYYY-MM-DD]`

## 阶段 2：检索、XBRL 与公司 Wiki（进行中）

### 检索

- 关键词 BM25，进程内倒排索引（`research/search.js`），可按公司、财季、章节过滤，命中话题标签的块加权 1.5 倍。没用 sql.js 的 FTS4：实测单次查询约 600ms，而且没有 bm25 排序。
- 中文问题先转成"英文检索词 + 过滤条件"（`research/query.js`），用规则表：公司名、财季写法、财务术语中英对照。没用 LLM 改写，是为了评估可复现、零成本，规则表的盲区也能在评估里直接看到。
- 评估集 `research/eval/retrieval-gold.json` 共 30 题（中文），覆盖 8 家公司的收入、分部、资本开支、毛利率、指引、风险。相关块的标准：来自正确公司和财季的申报，且正文匹配答案。答案逐字取自已入库原文；数值题另用 XBRL 交叉核对，核对不过评估脚本直接报错。
- 运行：`node scripts/research-eval-retrieval.mjs`

| 版本 | recall@5 | MRR@10 | 出处命中率@5 |
|---|---|---|---|
| v0 初版规则表 | 0.733 | 0.589 | 0.957 |
| v1 补"增长/同比"词、capex 加 additions、"全年"归 Q4 | **0.833** | 0.640 | 0.979 |

v1 的改动是看了 v0 的失败题之后做的。它们是通用规则，不针对某一题，但评估集只有 30 题，v1 的数字可能对这套题偏乐观。阶段 4 换用新题集再测。

v1 仍未命中的 5 题有个共同点：问的是某个具体分部或产品线（Microsoft Cloud、Google Cloud、AWS 增速、AMD 数据中心、博通 AI 半导体）的收入，而"revenue"这个词在每个块里都有，区分不出来。这正是向量检索可能补上的地方。

#### 向量检索对比（2026-10-21，结论：不接入）

两个本地小模型，在本机 CPU 上给全部 7857 个块生成向量，过滤条件和线上关键词检索相同。融合方式：BM25 前 50 与向量前 50 做倒数排名融合（RRF，k=60）。

| 检索方式 | bge-small-en-v1.5 recall@5 / MRR@10 | multilingual-e5-small recall@5 / MRR@10 |
|---|---|---|
| 关键词 BM25（线上现用） | **0.833 / 0.640** | **0.833 / 0.640** |
| 向量，查询用英文检索词 | 0.600 / 0.422 | 0.633 / 0.523 |
| 向量，查询用中文原问题 | 0.300 / 0.192 | 0.533 / 0.404 |
| 关键词 + 向量融合 | 0.800 / 0.559 | 0.733 / 0.603 |

- 两个模型都没有带来可度量的提升，融合后 recall@5 比纯关键词还低（−0.033 / −0.100），按阶段 0 定的规则不接入。线上不增加约 300MB 的模型内存，也不增加 embedding 依赖。
- 向量单路并非一无是处：e5 把关键词漏掉的谷歌云收入题排到第 1，把微软资本开支两题从第 3 提到第 1。但它同时把关键词本来答对的题挤下去（AMD 指引、台积电毛利率等），一进一出整体是负数。
- 关键词与向量都答不对的题：问的都是某个具体分部或产品线的收入（Microsoft Cloud、AWS 增速、博通 AI 半导体）。这类题的答案在财报的表格行和要点句里，单一检索词区分不出来，留给阶段 3：Agent 可以多轮检索，也可以直接查 XBRL 分部数值。
- 资源：每个模型约 45–50 分钟；全程排在工作区共享的渲染锁上（`_shared/locks/render.busy`），先来先到，跑完即释放。
- 复现：`research/eval/vector-exp/`（`export.mjs` → `run_queue.py` → `embed.py` / `evaluate.py`）。逐题排名存在 `results-2026-10-21.json`。

### XBRL 数值层

- `xbrl_facts`：8 家公司共 18347 条（companyfacts 中的 10-Q / 10-K / 20-F，窗口从最早一季往前再推 15 个月，够算同比）。同一期间有多份申报时保留最新那份，重述以最新为准。
- 单季值缺失时用 YTD 差分推算，并标 `derived`。常见情况：现金流量表只报年初至今（NVDA 10-Q 的 capex），10-K 只报全年（各家的 Q4）。已与原文核对：MSFT FY26Q4 capex $35.802B、NVDA FY27Q2 capex $2.677B。
- TSM 的 XBRL 截至 2026-10-21 只有 FY2024 的 20-F，FY2025 的 20-F 还没进 companyfacts。TSM 的季度数字只能从 6-K 原文里取。

### LLM 账本与预算

- 每次调用写一行 `llm_runs`：用途、公司、模型、输入输出 token、成本（优先用 OpenRouter 返回的 usage.cost）、耗时、是否成功。失败的调用也记。
- 硬上限在调用前判定，按"已花 + 本次最坏情况"算，超了就不发请求，并给管理员发邮件（每池每天一封）：
  - 日常：每天 $0.5、每月 $5（含 ask_company）
  - ask_company：每月 $3
  - 首次回填：总计 $3
  - 评估：每轮 $12
- 价格表里没有的模型拒绝调用：价格不明就守不住预算。

### 公司 Wiki

- 类别：业务分部、指标口径、管理层指引（含目标期间）、关键事件。
- 每条必须带逐字引文和块 id。程序在块里定位引文（容忍空白差异），算出原文字符区间；定位不到的条目丢弃，不让 LLM 自己评判出处。
- 同一项出现不同值时两条都保留：旧条指向新条，两条都标冲突。同一句原文换个说法不算新知识。
- 增量：处理过的申报不再调用 LLM；按申报日升序处理。
- 首次试跑：MSFT 一份 8-K，提出 14 条、入库 12 条，输入 5202 / 输出 1382 token，**$0.0019**，耗时 38 秒。
- **全量回填（2026-10-21，充值后）**：119 份申报全部处理，入库约 1200 条，**总成本 $0.50**。8 家公司并行，约 23 + 5 分钟。首轮有 7 份失败：6 份长申报的输出超过 3000 token 被截断，JSON 不完整；1 份网络断连。上限改为 6000 后重跑全部成功。
- **冲突口径收紧**：首轮按"同一项、值不同"标冲突，1043 条里标了 244 条。抽查发现多数只是例行更新，比如分部季度收入换了新数字，或同一个指标定义换了种说法，并不矛盾。现在只有"同一目标期间的管理层指引，数字变了"才算冲突，比如 GOOGL 2025 资本开支指引 $75B → $85B → $91–93B、META 2026 资本开支指引区间收窄，共 14 条。其他更新照样保留新旧两条（旧条指向新条），只是不标冲突。

## 阶段 3：研究 Agent 与笔记生成（代码完成，真实运行待 OpenRouter 充值）

### 数字从哪来

- 从缓存的 10-Q / 10-K 原件里解析 Inline XBRL（`research/ixbrl.js`），带维度（分部、产品线、地区），8 家公司 51 份申报共 50517 条事实。阶段 2 检索最难答的分部收入题，这里直接按 XBRL 字段取数。
- 指标表（`research/metrics.js`）全部由代码算出：本季、上季、去年同期、环比、同比。单季值缺失时用 YTD 差分推算（Q4 = 全年 − 9 个月；现金流量表只报 YTD），毛利率、营业利润率、自由现金流按公式推算，推算值都标 `derived` 并写明算式。
- 已与原文逐项核对：MSFT FY26Q4 营收 $90.01B、资本开支 $35.80B；NVDA FY27Q2 营收 $96.22B、数据中心 $89.02B、净利润 $59.69B、稀释 EPS $2.46、经营现金流 $24.08B（6M 74,421 − 3M 50,344）；AMZN AWS $42.23B。

### Agent 流程

1. 代码先算好指标表。
2. LLM 通过工具调用多步收集证据，最多 8 轮，最后两轮强制交稿。工具有：检索原文、读上季指引、读公司 Wiki、读股哨兵信号与产业链背景（只作背景）。
3. 调用 `submit_note` 交稿。每条陈述必须带出处：指标 id，或块 id 加逐字引文。
4. 程序自检（`research/verify.js`）：出处存在、引文逐字在块里、陈述里的每个数字都能在所引出处里找到、没有买卖建议、目标价或股价预测、摘要里的数字都出自已核对的陈述。不通过的把失败清单回喂模型重试一次，仍不通过的标"🔴 待人工核对"并保留，不静默删除。
5. "关键数字"表由程序直接从指标表生成，不经过 LLM。

初版和正式版：某季只有 8-K 新闻稿时出初版，没有 XBRL 指标表，数字只能来自新闻稿逐字引文；10-Q / 10-K 到了再出正式版。每次运行入 `research_notes`（版本号递增），记 token、成本、耗时、LLM 调用次数。

运行：`node scripts/research-note.mjs MSFT FY2026Q4 --out=<目录>`

### 真实运行（2026-10-21，deepseek/deepseek-v3.2）

样例笔记：[`docs/research-agent-samples/`](research-agent-samples/)，MSFT FY2026Q4 v4、NVDA FY2027Q2 v3，含 Markdown 与 JSON。

| 版本 | 结果 | 调用次数 | 输入 / 输出 token | 成本 | 耗时 | 说明 |

每份笔记 $0.013–0.023，耗时 2–8 分钟，主要是 deepseek 的响应速度。笔记里的数字区由程序生成，与原文逐项核对一致。

核对器在真实运行中修了三处，都配了反例测试，确保数字错、量级错、增速错仍判失败：
1. 中文"亿 / 万"与英文 billion / million 的单位换算；
2. 去掉模型写进正文的出处标记；
3. 块号差一位时，在同一申报的相邻块里找引文（引文仍须逐字存在）。

**核对器目前的盲区**（如实记录，阶段 4 要量化）：它只核对"数字能在所引出处里找到"，不核对"出处在语义上支持这个说法"。例子是 NVDA v3 的"非 GAAP 毛利率 75.0% 在指引范围内"：结论本身对，新闻稿实际值确是 75.0%，但引的出处是上季的指引原文，不是本季实际值。阶段 4 的"出处准确率"指标就是要量出这类问题，候选方案是要求"实际值"类陈述必须引本季的申报。

### 已知局限

- 指标表纳入单维分部、产品线、地区收入，以及"合并口径轴 + 分部轴"的双维分部（NVDA、GOOGL 的写法）。其他多维组合（如 META "分部 + 产品"）跳过，避免同一笔收入计两次。
- 公司改了 XBRL 成员名时，单季值推不出来（MSFT 10-K 把 Gaming 改名为 XBOX），这类成员记入"未披露"，不推测。
- TSM 季度新闻稿 EX-99.1 只有约 4K 字符，详细的管理层报告是 PDF，不在 EDGAR。季度分部和平台数据要从季度合并财报里取，阶段 3 需要专门处理。
- 修正案（10-K/A、6-K/A）不收。AMD 有一份 10-K/A，多半只补 Part III。
- 章节切分基于 Item 标题规则，已用 11 份真实申报校验，覆盖 8 家公司的版式。新发行人或版式大改时，可能把章节归到 `other`。数据质量检查会把缺失的必需章节报出来。
- research.db 是 sql.js 内存库，约 30MB，部署到云端时要算进内存。只保留 8 个季度可以把它控制在这个量级。

## 阶段 4：评估

金标：`backend/research/eval/notes-gold.json`，8 家 × 最近 2 个正式版财季 = 16 份 × 10 个事实 = 160 个。其中数值 144 个，取自 XBRL（TSM 取自新闻稿表格）；下季收入指引 12 个，逐字取自新闻稿；"未披露" 4 个，是 MSFT、GOOGL 的新闻稿不给数字指引。全部由程序生成后冻结，评估不重新出题。指标定义见 `backend/research/eval/notes-eval.js` 文件头。

**强模型经 OpenRouter 不可用**：Claude Opus 5.5 在 OpenRouter 本机所在区域被拒（403 "This model is not available in your region"），16 次请求均未计费。Sonnet 5.5、GPT-5.5 同样被拒。可用的强模型候选：x-ai/grok-4.7（$2 / $6）、z-ai/glm-5.3-prime（$2.8 / $8.8），价格为每百万 token 输入 / 输出。强模型对比最终改用本机 Opus 5.5（见下文"改进后对比"）。

**打分器修正后重打分**（2026-10-21，不重跑模型、不改金标）：首次打分数值准确率 87.5%，逐条复核 15 个"错"，其中 9 个是打分器误判：
- "营业利润率 17.3%"被当成"营业利润"；"Reality Labs 减少营业利润 40.3 亿"被当成公司营业利润；
- 年份识别把"2006.1亿美元"的 2006 当成年份删掉，"1970-2020亿美元"整段消失；
- 区间写法"1970-2020亿"只有后一个数带单位。

修正后数值准确率 94.7%。

**deepseek 一轮的真实错误**（6 个数字错 + 4 个"未披露"误报），按原因：
1. **TSM 新台币量级读错**（4 处）：新闻稿表格单位是"新台币百万元"，模型把 1,270,381 百万写成"1,270.38亿"，少了 10 倍。自检已判为待人工核对，但仍算错。改进：在 TSM 的提示词里明确单位换算（1,270,381 百万 = 12,703.8 亿），并把表格单位行一并检索给模型。
2. **把上季指引当成本季指引对照**（1 处，META）：拿上季的指引区间对照、还漏了量级。改进：get_prior_guidance 返回时标明"这是上季给本季的指引"，下季指引另给一个工具结果。
3. **用了增速、没写金额**（1 处，GOOGL Services）：陈述只写同比 16%，金标是金额。这不算编造，但打分记为未答对。改进：在提示词里要求分部陈述"金额 + 同比"成对出现。
4. **"未披露"误报**（4 处，比例 2.6%）：GOOGL 稀释 EPS、AMZN 毛利率、NVDA 资本开支、AMD 营业利润，指标表里都有，模型却列进"未披露"。改进：程序在交稿后自动删掉"未披露"清单里指标表有值的项，并记一条提示。

**（改进前）覆盖率 70.6% 不达标**（目标 ≥ 90%）：10 个关键事实里平均只提到 7 个，漏得最多的是资本开支和稀释 EPS。原因：提示词只要求"3–6 条要点"，模型按自己的判断挑重点。改进：要点数量不变，在提示词里列出这 10 个事实必须覆盖；或由程序把没覆盖的金标事实直接以"关键数字"陈述补进要点，这一步不经过 LLM。

### 改进后对比（2026-10-21）

改进内容：
1. **补全漏掉的关键指标**：交稿后由程序把模型漏写的关键指标补成陈述，标记为 `generated`，数字直接来自指标表，不经 LLM。
2. **清理"未披露"清单**：把指标表里其实有值的项从清单里删掉，并在笔记里记下删了哪些。
3. **TSM 提示词写明换算**：表格单位是"新台币百万元"，提示词里给出到"亿"的换算示例。
4. **上季指引写明适用季度**：`get_prior_guidance` 返回结果时注明"这是上季对本季的指引"。
5. **核对器拦截未来信息**：不许引用本季最后一份申报之后提交的文件。

**本机 Opus 5.5 怎么跑**：OpenRouter 的 Opus 5.5 在本区域不可用（403），所以改由本机 Claude Code 的 Opus 5.5 子代理充当"写稿模型"。工具、指标表、提示词、自检和打分全部相同，用 `scripts/research-tool.mjs` 实现，唯一的区别是由谁写稿。和 API 路径相比有三点不同，如实说明：
- **成本未记账**：token 与成本不经 OpenRouter 记账，表里留空，不做估算。
- **延迟不可比**：耗时包含命令行调用开销，不能与 API 延迟直接对比。
- **工具输出被截断**：Claude Code 显示过长的命令输出时会省略中段，`[N chars omitted]` 那部分子代理看不到，导致 6 份笔记的首稿引用了看不到的部分、各用掉一次重试；最终 15 / 16 份通过自检。这对 Opus 不利，与模型能力无关。

**结论**：
- **事实覆盖率达标**：改进后 70.6% → 94.4%（deepseek）、95.0%（Opus），主要来自程序补全。"未披露"误报 2.6% → 0%。
- **数字准确率**：Opus 100%，deepseek 94.0%。deepseek 剩下的 9 个错里，6 个是 TSM 的新台币量级错。提示词明确写了换算，它仍然把 1,270,381 百万写成"1,270.38亿"，少了 10 倍。Opus 的做法是照抄原文写法（"NT$1,270.38 billion"），根本不做换算。**改进方案**：这一步不要交给模型。对 TSM 由程序先把表格解析成指标表（与 `gold.js` 的 `tsmFactsFromRelease` 同一套解析），让 TSM 和其他公司一样只按指标 id 引用数字。
- **出处准确率**：Opus 99.6%，deepseek 89.6%。deepseek 的失败主要集中在 TSM（上面那类量级错会触发自检失败）和少量块号记错。
- **捏造指引两边都是 0**。MSFT、GOOGL 不给数字指引时，两个模型都没有编，写的是"无法对照"。
- **生产默认模型仍用 deepseek**：每份 $0.02，覆盖率与 Opus 持平；数字差距集中在 TSM，用程序化的修法就能补上。强模型可作为待人工核对笔记的复核方案，阶段 5 再定。

**grok-4.7（OpenRouter，可记账的强模型）**：数值准确率 100%，覆盖率 95.0%，出处准确率 97.6%，16 份共 $2.15，每份 $0.13，约为 deepseek 的 6.5 倍。P50 延迟 85 秒，三个模型里最快；P95 416 秒，由 TSM 一份拖长。TSM 新台币金额它全部写对，避开了 deepseek 的量级错误。

据此对阶段 5 的建议：
- **默认**：deepseek 生成，成本低。
- **复核**：自检有"待人工核对"项、或公司为 TSM 时，改用 grok-4.7 重写一次。按 16 份里约一半需要复核估，平均每份约 $0.08，远低于每月 $5 上限。

是否这样做，由用户在阶段 5 拍板。

打分器在 grok 轮又修了一处：评估 grok 时，"下季收入指引"只认"第X季度"写法，漏判了"第三季的展望"；"未披露"清单里的"全年营收指引"又被误配成该事实。Opus 与 grok 因此各被冤枉 1–2 个"未披露"误报，修正后均为 0。四轮全部用同一版打分器重打分，没有重跑模型，也没有改金标。
